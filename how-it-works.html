How It Works

The maths and the code behind Maximum Radler. Minimum Regret.

01Hi!

I'm Anastasiia, a mathematics student, and I've spent about four years working on mathematical optimization problems.

Optimization problems come in all shapes and sizes. Sometimes, like here, the goal is simply to find the cheapest Radler and save a little money.

Or we could make it more complicated. What if we wanted to minimize the cost of getting drunk and the distance from where we're standing right now? Why not? That's a perfectly good optimization problem too. (To be clear: that one is just an idea. This website doesn't do it.)

But you're here to see how this particular project works. So here's a little background, the mathematical formulation, and how I actually built it.

02The mathematical problem

At its core this is a discrete price minimization problem: there is a finite set of supermarket offers, and we pick the cheapest one. No calculus, no continuous variables, just a careful definition of what is allowed to compete.

For each city we solve two separate problems: the cheapest single bottle or can, and the cheapest beverage per liter. They answer different questions, so they can (and sometimes do) have different winners.

Cities and sets

C={Garching, Munich},c∈C
  • Ic is the set of all eligible Radler offers in city c.
  • Ic∗ is the subset of Ic containing only offers for an individually purchasable single bottle or can, with a known deposit and no additional minimum purchase requirement.
Ic∗⊆Ic

Every single bottle is also an offer, but not every offer is a single bottle. For example:

Offerin Icin Ic∗
Lidl: one 0.5 L bottleyesyes
Lidl: six 0.5 L bottlesyesno
REWE: one 0.5 L canyesyes

Parameters

Each offer is identified by an index i. For every offer we know:

SymbolMeaning
αiPackage price excluding deposit (€)
βiRefundable deposit (Pfand) for the package (€)
γiNumber of containers in the package
δiVolume per container (liters)
εiIndividual purchase availability: 1 if one container can be bought on its own at this price, otherwise 0

With these symbols the single-container set reads

Ic∗={i∈Ic:εi=1,γi=1}

where, in addition, the deposit βi must be known and the offer must not require buying more than one container.

Problem 1 · Minimum price per bottlemini∈Ic∗(αi+βi)
Problem 2 · Minimum price per litermini∈Icαiγi⁢δi

Problem 1 looks for the cheapest individually purchasable bottle or can, including the refundable Pfand: what you actually pay at the till for one Radler.

Problem 2 looks for the lowest price per liter of beverage, excluding Pfand (you get the deposit back, after all). Single containers and multipacks both compete here.

Example with the shelf prices observed on 13 October 2026 at Lidl Schleißheimer Straße: the single bottle gives 0.45+0.25=0.70 € for Problem 1, while the six-pack gives 2.69/(6·0.5)≈0.897 €/L for Problem 2, just ahead of the single bottle's 0.90 €/L.

03Algorithm

Because every set is finite (a few dozen offers at most), the website simply checks them all. This is what index.html does every time the page loads:

read records from data.json

for each city c in {Garching, Munich}:
    I_c  ← { r : r.city = c and eligible(r) }
    I*_c ← { r ∈ I_c : r.single and r.count = 1
                      and r.min_qty ≤ 1 and r.deposit is known }

    best1 ← offer in I*_c with smallest  α + β         # price + deposit
    best2 ← offer in I_c  with smallest  α / (γ · δ)   # price per liter
                                        # ties: most recent observation wins
    show best1 and best2 with branch, address and map link
         (or "No verified prices yet" if the set is empty)

eligible(r):
    r is an alcoholic Radler                   # no alcohol-free, no other beer mixes
    and r.status = verified                    # no unverified, personalized or online-only reference prices
    and (r is not a loyalty price or the discount is public)
    and valid_from ≤ today ≤ valid_to          # expired or future offers are skipped

In code, this is plain JavaScript: filter builds the sets, sort orders them by the objective, and the first element is the minimum. There is no linear or mixed-integer programming solver involved, and none is needed: a finite minimum can be found by comparison.

Complexity. With n records in total, each of the four searches (2 cities × 2 problems) filters all records in O(n) and sorts the remaining ones in O(nlogn), so a page load costs O(nlogn) time and O(n) memory. A single linear scan would get it down to O(n), but with a dozen records the difference is a few microseconds; sorting keeps the tie-breaking rule simple.

04Where the prices come from

  • Shelf-label photos. Prices I (or visitors) photographed in a store. Visitors send photos through the "Report a different price" form; I review every photo by hand before anything is added. The photos themselves stay private and are never published on the website or in the repository.
  • Official online prices. Prices from a supermarket's own product page, such as ALDI Süd's.
  • Automated Kaufland offers. A small Python script reads Kaufland's public, store-level offer data for its Munich branches every day. The other chains can't be collected automatically in a permitted, reliable way (bot protection, no store-level prices online, or offers that only appear after choosing a store in the browser), so they stay manual.

Not every price is allowed to win. Each record has a status:

Kind of recordRanked?
Verified branch observation: a shelf photo or a store-specific retailer offer, with a known branch addressYes
Official online reference price: real and official, but not confirmed for a particular branchNo, listed only
Expired offer: the promotion's end date has passedNo, listed only
Unverified or personalized price: e.g. an app coupon only some people getNo, listed only

Prices observed more than 14 days ago are flagged "may have changed", but they are not excluded automatically. A shelf price doesn't expire on a schedule, so it stays until a newer observation replaces it.

Technologies

  • HTML and CSS for the pages, with no frameworks, web fonts or images.
  • Vanilla JavaScript in the browser for eligibility filtering and both price calculations.
  • JSON (data.json) as the price database, edited by hand or by the collector.
  • Python 3 for automatic collection and validation, using only the standard library: urllib.request, json, re, html, datetime, pathlib and sys.
  • GitHub Actions runs the collector every morning and re-validates data.json after every change; the collector only commits data that passes validation.
  • GitHub Pages hosts everything for free.
  • FormSubmit delivers the price reports and their photos to my inbox.

06What could come next

The current model is deliberately simple. These are possible future extensions, not current features:

  • Finding the cheapest Radler within a given travel distance.
  • Considering travel costs alongside the beverage price.
  • Minimizing total spending for a given quantity of Radler (say, for a party).
  • Multi-objective optimization trading off money against travel distance.
  • Integer programming for combining package sizes under a budget.
